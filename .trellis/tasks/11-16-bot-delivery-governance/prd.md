## 执行顺序

用户最新要求不再等待群任务暂停，直接落实本规范；不主动停止现有工作或恢复已暂停的原目标。配置和可执行验证先完成，需真实 PR 的端到端结果在有合适真实任务时核验，未取得证据前保持待验。

## 需求

1. 每项任务先核对真实仓库、远程、开发分支、最新基线、执行身份和权限、分支保护、CI、已有任务与 PR；明确需求、负责人、写集、交付物与验收。不能将某个项目的名称、目录、权限或例外套用到其他项目。
2. 按最新群公告与管理员职责的原文整体整理并合并重复规则；保存前完整备份当前原值，保存后重新打开并逐项核验内容及权限。保持群原有有效职责、项目约束和具体任务的授权例外。
3. Developer 按项目规则执行经授权的常规开发、验证、提交、推送和 PR；QA、Reviewer 根据任务要求独立核验；管理员核对需求、变更、CI、审批、保护、冲突及当前源/目标提交，在条件满足后由其通过平台合并并核对远端状态。
4. CI 不可用、失败、未完成或状态不明时不得当作通过；缺审批、冲突或权限不足时停止受影响步骤并记录接手者。远端操作结果不明时先查询 PR 和分支，不重复创建、合并、强推或覆盖其他工作。
5. 发布和部署仅遵循明确发布需求或项目已有发布触发条件、维护者权限和现行流程；日常 PR 合入开发分支不等于发布。不得为验证自动流程而发布、触发部署或绕过项目保护。
6. 如需由 Bot 自动推进，首先以真实任务确认 Developer 交接能唤醒管理员及其后续行为；不同于 GitHub 的排队式 auto-merge，Bot 条件齐备后可调用普通 PR 合并。尚未证实的后台订阅、轮询和定时唤醒不得表述为已实现。
7. 持续观察真实 Bot 的交接和同一补丁指纹的 QA/Reviewer 验收；记录负责人、执行者、原始失败、结果、未覆盖范围和管理员结论，不把本助手的文件核查当作团队独立验收。
8. 本助手只做已授权的配置整理、核验与只读跟踪，不代办团队技术任务、不主动向 Bot 发消息；不读取用户 `~/.dsh`、不截图、不触碰既有工作树改动或扩大权限。需要独立界面时遵守不干扰其他会话的要求。

## 范围外与待核实

- 本任务不修改 DSH 本体或用户 DSH 数据，不自动创建定时任务、开启 GitHub 设置、发布、部署，亦不自行实施团队产品代码。
- 管理员职责保存的实际通知、Bot 的执行身份及权限、PR 唤醒方式与正常任务的端到端结果仍需按计划核实；群公告已按保存时的实时配置验证。
- 如发现现有交接不足以支撑所需自动化，应先说明具体缺口、影响和可选方案；任何新增长驻服务、事件订阅或改变仓库保护均单独评估。
