# 群自动交付与分支规范设计

状态：实施中。群公告已保存并重开核对；管理员职责仍待保存，自动触发和真实 PR 合并尚无验收证据，仓库设置未变。

## 交付路径

1. **接收与拆分**：管理员确认真实项目、需求、验收、负责人、仓库、基线和工作区；已有任务先复用，并按需分配 Developer、QA 和 Reviewer。
2. **开发与交接**：Developer 依据项目规定和任务授权建立独立分支、实施、验证并发起 PR，在群中交接需求、PR、待审源提交、验证结果与剩余问题。团队之间的消息由真实 Bot 和用户按已有协作方式处理；本助手不代发。
3. **条件检查**：管理员读取当前 PR、目标分支及仓库规则，核对需求、完整差异、冲突、检查、必要审批、源/目标最新提交和执行身份。QA/Reviewer 的职责和独立验证结果按该任务的验收要求核查。
4. **合并与复核**：条件全部满足后，管理员使用项目允许的方式合并；核对 PR 状态、合并提交与实际远端开发分支，再登记交付。任务状态为完成的前提是必需证据齐全。
5. **异常**：检查未完成、失败、冲突、审批或权限缺失时，记录明确阻断及接手者。操作结果不明时先查询远端 PR 和分支；状态变化后重新核对受影响条件。

## 自动化与触发边界

- 首选复用项目已有团队交接：例如 Developer 在 PR 就绪后有效通知管理员，由管理员在收到任务后主动完成核验和合并。此路径必须通过真实群消息及后续动作验证；单次成功只证明该次。
- 已知 GitHub `allow_auto_merge=false` 限制平台排队式自动合并，不阻止具备权限的 Bot 在全部检查完成后执行普通 PR 合并；是否具备身份、权限和可靠唤醒能力仍须实际核验。
- 尚无证据表明 PR 事件订阅、定时轮询或无人值守唤醒存在。若真实任务验证发现交接不足，先记录具体失败和影响，形成具体方案再处理；不在规划阶段新增守护进程、定时任务或 GitHub 配置。
- 如 CI 尚在运行，记录等待状态及实际可用的后续唤醒方式；只有观察到后续执行和结果，才能宣称该次自动闭环。工作区源码 `ds-bot/src/host/goals.js:591` 在群目标活跃且满足条件时会发起空闲检查，管理员 pass 或连续两次无进展后进入 idle；`ds-bot/src/host/groups.js:1917` 的群消息入口包括用户消息、定时任务、Bot 发布及群目标消息。该机制本身不是 CI 完成订阅；运行实例版本、群目标状态和实际后续触发仍须核实。

## 配置与回退

- 通过已登录、不会扰动其他会话的界面确认目标群。先分别完整读取并备份最新群公告与管理员职责，记录时间、原文和指纹；以当前原文为基础合并重复约束、重排结构，旧草案仅作参考。
- 公告和职责分别保存、关闭并重开核对完整内容；同时核对群成员、主持方式、管理员权限等非目标配置。若保存前原文已经变化，先重新读取并比较，避免覆盖并发修改。
- 工作区源码表明修改 Bot instructions 在某些条件下会向其私聊投递更新，但运行版本及实际会话影响待核实。用户于 11:42 明确接受本次保存可能产生的系统通知；不主动发送其他 Bot 消息，保存前重新核对原值，窗口切到其他会话时停止操作。
- 回退时先确认当前内容仍为本次写入版本，再用同次原文备份恢复并重开核对；若其他人已经修改，先比较并保留其变化。回退不涉及重置仓库、清理用户数据或更改权限。

## 项目、发布与证据边界

- DS Bot 按 `dev` / `main` 和仓库贡献规则；各项目的远程、分支名称、保护、权限与 CI 以执行当时事实为准。上游只读与 Fork 写权限不得混淆。
- 稳定自动恢复专项保留不提交、不推送、不创建 PR 或发布的特殊约束；不把该专项当作普通 PR 合并验收。发布仅依明确需求或现有项目触发规则及维护者权限办理。
- 配置生效验证与真实任务端到端验证分开记录；核对同一补丁的 QA/Reviewer 独立报告、测试执行者、实际运行环境和未覆盖范围。不得将自报、派单回执或单纯的 SHA 核对视作测试通过。
- 不读取用户 DSH 数据或密钥，不截图；检查疑似含密钥的证据时只记录路径、行号和类别。外层系统沙箱与独立 HOME、DSH_HOME 的范围分别记录。
