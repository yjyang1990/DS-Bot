# DS Bot 开发与交付群：分支管理与合并规范

状态：群公告已于 2026-11-16 保存并重新打开核验；管理员 Bot 全局职责尚未更新，真实 PR 自动交付尚待验证。旧追加式公告草案仅作参考，不直接应用。依据用户 2026-11-16 的明确要求，为本群项目提供常规分支、PR 与受条件约束的自动合并流程。实际仓库的规定、当前权限和分支保护优先；项目之间的授权不自动相互转移。已有任务明确约定的限制继续适用。

## 每个项目开始前

1. 确认实际工作区、仓库和远程地址、开发与发布分支名称、远程最新提交、仓库贡献流程、分支保护、当前执行身份、合并权限和 CI。未核实的事项记录为待确认，不新建同名替代分支。
2. 确认需求编号、目标和验收，查找已有任务、分支及 PR；原则上一项需求对应各仓库各一个功能分支和 PR。已有对应工作时先确认并复用。任务记录关联需求、仓库、基线、分支和负责人。
3. 从对应远程最新开发分支建立符合该仓库命名规则的任务分支。并行工作划定写集，必要时使用独立工作区或 worktree，保护其他任务和未提交改动。

## 日常开发和合并

1. Developer 依据需求与仓库流程完成改动及验证，检查变更范围，避免混入其他任务和敏感信息；按仓库规范提交、推送任务分支，创建或更新指向实际开发分支的 PR。PR 记录需求、实现、验证结果和剩余问题。
2. 管理员收到 PR 后核对需求、完整差异、验收条件、冲突、CI 和仓库保护；确认所核验的 PR 源提交及目标分支仍匹配最新状态，变化时重查受影响部分。检查必须来自实际仓库和此次 PR；CI 不可用、未完成、失败或结果不明时不将其视为通过。
3. 在执行身份具备相应权限、必需审查和检查全部满足时，由管理员通过托管平台执行合并，并核对 PR 状态和远程开发分支的合并结果，再登记任务；项目约定允许时清理已合并且不再使用的功能分支。若平台的排队式自动合并开关关闭，可在条件全部满足后使用普通 PR 合并；不得将排队状态当作已完成合并。
4. 检查失败、冲突、审批或权限缺失时停止合并并交接；操作结果不明时先查远程 PR 和分支，避免重复创建或执行。不得绕过保护、强推或覆盖共享分支，不清理其他任务的工作。

## 发布

仅在用户提出明确发布需求或项目既有发布触发条件满足后，依据仓库发布流程，从开发分支向发布分支发起并检查发布 PR；仅在维护者权限、审批、验证及保护条件满足时合并并核对结果。标签、发布记录和部署按项目既有流程和适用的明确要求处理。普通功能合并不构成发布。
